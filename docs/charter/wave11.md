## 〇、这一波的主线：**凭据与身份**

十波下来，判定层已经很硬——五道门、四档处置、组织/用户组子树展开、审计链与 SIEM 外送、
温备、隐身八态回执，都做到了单一执行方 + 三态 + fail-closed。功能面上真正的空洞已经不多。

而本波三份规划**同时**把同三条排进前四，它们不在判定层，在**它下面那一层**：

| 判定层以为的事实 | 实际 |
|---|---|
| 「这个账号的口令在外部目录里，本地没有」 | 控制面每重启一次，全体外部账号就获得公开口令 `baidi@123` |
| 「这条隧道连接是 zhang.wei 发起的」 | 只是「这条连接的源 IP 上，最近有人敲过门」 |
| 「这个管理员已被禁用」 | 他手里那张 8h 令牌仍是完整管理员 |

判定层再严，判据本身错了就全错。所以本波的取向是：**先把身份与凭据这三条堵死**，
再补默认姿态与交付腿，最后才是展示与记账。

边界表达是白帝最强的部分，本波要守住的正是它——**不许为了让某一格变绿，
把「不可判定」塌成好值**。

## 一、行动清单

### A. 凭据与身份（会当场做出错误的安全判断）

**1. 外部目录账号不再在每次重启后拿到公开口令 — S ✅ 已完成（6486cea）**

`ensureCredentials` 的 pass_hash 回填每次启动都无条件跑，判据 `pass_hash=''` 同时命中两种
互斥语义：史前迁移库的本地用户（该补）与**外部目录账号**（恒不该有本地口令，CLAUDE.md
写成不变式）。后果：控制面每重启一次，全体 LDAP/AD/RADIUS/OIDC 账号都获得可用的
`baidi@123`；叠加门户「先本地、后外部」，知道外部用户名即可冒充，全程不触达外部认证源，
审计里是一次完全正常的本地登录。二阶后果：`guardLocalCredentialForAdmin` 判「是不是外部
账号」用的正是 `PassHash == ""`，哈希被填上后**那道守卫整个失效**，外部账号可被提为管理员。

**实测复现**（不是读代码推断）：绑一个 LDAP 身份 → 跑一次 `ensureCredentials` →
`auth.VerifyPassword(hash, "baidi@123")` 通过。

修法与 `adminRoleBackfillMarker` 逐字同款：回填改一次性标记 + 那唯一一次也排除外部绑定行 +
存量污染逐个点名清理（判据取「有绑定 ∩ 口令恰为出厂口令」的交集，以免抹掉管理员刻意
设置的补救口令）。清不到的一类已写进注释：认证源被删后的孤儿账号在库里与「持出厂口令的
本地账号」完全同形，只能靠启动期自检点名。

6 条用例，三处修复各做过一次变异实跑。**第一轮变异 1 逃逸**（`openTestStore` 已落标记，
`NOT EXISTS` 没被走到），据此补了针对「已配置 LDAP 的存量库升级」的专项用例。

**2. 删掉 `roleFromDisplay` — S ✅ 已完成（372ec99）**

wave10 修的是 `seed()` 那处（zhang.wei）。同一个 helper 还有两个调用点没被覆盖，其中
`ensureCredentials` 的 role 回填**每次启动都跑**且排在 `backfillAdminRoles` **之前**——于是
存量库升级那一刻，任何展示标签里带「管理员」三个字的普通用户被连续两跳静默提成超管。
两处改成显式声明（不声明即 user），内置 `admin` 显式豁免（防自锁链的锚点），helper 删除。

**3. 给 L4 隧道连接一个自带的身份：票据化前导，放行表退回纯端口闸 — L（本波唯一的 L）**
PRD FR-INTRO-06(P0) / FR-ARCH-02 / FR-AUDIT-05

`spa.Allowlist` 是 `map[源IP]entry`，`entry` 直接携带 user/role，`Allow()` 整条覆盖；
`proxy.handle` 每条 TCP 流现查 `al.Allowed(ip)` 取身份，那个身份是 `reg.Authorize`、
`tunnel-allow` 审计与 `track`/`KillUser` 的唯一来源。隧道上**没有第二个身份来源**：
TLS/TLCP 都不设 `ClientAuth`，前导只有 `CONNECT <rid>`，敲门令牌只走 UDP 口。

于是门槛不是「持有白帝账号」而是「**共享源 IP**」——同出口任意主机（咖啡厅、酒店、
企业 NAT、CGNAT、云主机同公网 IP）只要有人处在放行窗内，直连隧道口即继承其全部
`AllowUsers`、JIT 与降权结论；两个账号还会随各自 15s 保活来回刷写身份。连带旁路强制下线：
`RevokeUser(A)` 按 `e.user` 匹配，末次敲门者是 B 时整条不匹配 → 漏撤窗。

ARCHITECTURE:868 声明的是**设备维度**缺失，:1730 声明的是**活跃时刻**互相顶替且方向是
「不该踢的不踢」——两条都不等价于「不同账号互相继承资源授权」。**反向证据更强**：
第五节「五道门」还断言过「即使剖面被完整泄露，攻击者也拿不到任何访问权」。

**形态**（照 B/S 那条已验证的链复刻，不发明新机制）：控制面在 `handleKnockToken` 同一次
调用里附发 `use=tunnel` 短时效票据（第四把密钥 `BAIDI_JWT_TUNNEL_KEY`，use 语义闸三向扩
四向，绑 `gw`=网关 CN）→ 客户端挂在前导上 `CONNECT <rid> <ticket>` → 网关 `-jwt-tunnel-pubkey`
验签取身份，`al.Allowed(ip)` 降级为纯端口闸（只回 ok）。`internal/auth` 仍不加 Sign。

**五条陷阱**：① 票据**不做 jti 一次性**（会把控制面放进每条业务 TCP 的数据路径，与 30s
fail-closed 窗口叠加后抖动即断流）——理由必须写进注释，否则下一个人「照抄 web 票据」
会顺手加上；② **绝不接受客户端自报账号名**；③ 别用「一个 IP 只许一个账号持窗」当省事修法
（那是拒绝服务不是收敛授权）；④ 逃生舱 `BAIDI_GW_TUNNEL_ID_STRICT=0` 但**默认严格**，
回落每次留痕且在网关页可见；⑤ `Allowlist` 键必须同批改成 `(ip, 账号)`，否则 `RevokeUser` /
`Reap` / `-pf` 回收 / `Sessions()` / `ActiveCount()` 仍把同出口两人混成一条。

**回归缺口**：现有 `proxy`/`spa` 用例全是单账号 127.0.0.1，**在结构上无法区分**「按 IP 定身份」
与「按连接定身份」两种实现。必须新增「两账号同 IP 交替敲门」的用例。

**4. 给会话令牌一条真正的注销路径 — M**　PRD FR-SYSCFG-09/11 / FR-MON-13

`auth.Middleware` 只验签名与 use 白名单、不查任何库、无吊销表；`AdminRoleFor` 的 SQL 只筛
`u.role='admin'` **不筛 `u.status`**；`requireUser` 更是纯令牌判定。于是「禁用」「锁定」
「强制下线」「闲置自动锁定」四条处置对在手的 8h 令牌全部无效——管理员账号被盗后的标准
处置点完之后，攻击者仍是完整管理员。同批修 G12：强制下线只封 5 分钟、「已下线」标记
永不清理（用户自动重连后仍显示已下线且再也点不到那个按钮）。

**形态**：`users` 补 `tokens_valid_after` 列（**回填 0/不限**——回填成 now 就是升级那一刻
全员掉线，用例要正面钉住「升级后既有令牌仍可用」）；比对点收在 `currentAdminRole` 已有的
那一次按账号取数上，拿 `Claims.Iat` 比，别为它多打一次库；写值方只有一条 `revokeSessions(account)`，
四条处置路径全部走它。**别做成通用 JWT 吊销表**（每请求查库 = 同步瓶颈），
**别做成全局值**（任何一次处置会把全体管理员一起踢下线）。

**13. NAT 自伤 DNAT 与隐身攻击面 — M ✅ 已完成**　PRD FR-NAT-12/13 / FR-SEC-SPA-05

`NATWarnSPA` 是个**常量字符串**，启用 NAT 就无条件挂出来；它不检测「这条 DNAT 是不是把
网关自己的 18201/18443/18444 发布出去了」。一条 DNAT 可以把整个零信任接入面从公网露出来，
入口 200 OK、数据面照灌 prerouting。同批：「攻击面 = 0」的前提集补上 DNAT 发布的端口。

**落地**：① 执行方 `store.natSelfPublish`，接在 `normNATPolicy` **末尾**（`TranslatedPort` 留空
由归一补成 `DstPort`，提前查就放过「发布端口=隧道口、转换端口留空」这条写法——有变异用例钉住）。
拦两种形态：转换后目的 = 网关自己的监听口 / 对外发布端 = 网关自己的监听口，两条拒绝文案各写清后果
（前者是「给接入面再开一扇控制面不知道的门」，后者是 dstnat 排在路由决策之前 → 全员拨号超时而
心跳出向照常在线）。**端口取自心跳自报**（`api.natListenOf` → `store.NATListen`），`Reported=false`
退守出厂默认端口并当面写明「保守判定，等心跳上报一次后重试」。② 断言判定收在后端一处
`api.stealthClaim`（隐身逐台 armed ∧ 无七层敞口 ∧ 无 DNAT 敞口且判得出来），前端只渲染
`stealthClaimOk`——前提集分散在两条轨上时，加一条必然漏改其中一处。DNAT 敞口的判据是网关回执
`applied` 而非库里 `enabled`；判不出来的（离线 / 旧网关不上报 / 策略表读失败）单列且同样按下断言。

**复核修正（主控复核推翻了清单的一句措辞）**：清单原文说这类 DNAT「一条就能把整个零信任接入面
从公网露出来」并援引 `NATWarnSPA` 那句「隐身对它失效」。逐条核过 `gateway/firewall/baidi-nft.sh`
之后**措辞收窄了**：nft 的 `input` filter 钩子看到的是**转换后**的 dport，所以 DNAT 到网关**自己**
的隧道口时，`tcp dport <proxy> drop` 那条规则仍然命中，隐身**没有**失效（`NATWarnSPA` 那句针对的
是 DNAT 到**内网主机**——那种流量走 forward 链，filter input 的规则确实碰不到，那句话本身没错）。
真实危害是另外三条，全部成立：七层 Web 口本就不受隐身保护、隐身默认没开（`WITH_STEALTH=0`）时
净新增一个可探测端点、以及控制面对「接入面到底在哪」的记账整个失真。代码注释与拒绝文案按核实后的
措辞写，没有沿用清单原话。

⚠ **G33（内核态隐身放行侧三处坏掉）本波只做取证不改代码**：三条子断言全是读代码推断，
本项目没有 root 实机，而 pf/nft 的规则求值顺序属于「读源码看着对、上机就不是那回事」
的一类；结论若反了，改动方向会正好把当前能用的放行链路改坏（全员连不上，正是
2026-09-03 那次 orphan-ruleset 事故的形态）。**先在 Linux(nft) 与 mac(pf) 上各抓一份真实
规则文本贴进本 charter，再决定动不动代码。**
